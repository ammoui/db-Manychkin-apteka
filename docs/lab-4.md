# Лаба 4. Транзакции и доступ

**Цель:** воспроизвести ситуацию, когда два пользователя одновременно ломают данные, и исправить её. Закрыть базу от приложения так, чтобы оно могло только то, что ему нужно.

## Теория

**Транзакция** это группа операций, которая выполняется целиком или не выполняется совсем:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- зафиксировать; ROLLBACK отменил бы обе операции
```

Если в середине транзакции произошла ошибка, база отменяет все её изменения.

**ACID:**

| Буква | Свойство | Смысл |
| --- | --- | --- |
| A | Atomicity, атомарность | Всё или ничего |
| C | Consistency, согласованность | После транзакции все ограничения соблюдены |
| I | Isolation, изоляция | Параллельные транзакции не видят незафиксированных изменений друг друга |
| D | Durability, долговечность | После `COMMIT` данные сохранятся даже при сбое |

**Гонка (race condition)** возникает, когда проверка и действие выполняются отдельными шагами. Две сессии одновременно проверяют «есть ли свободное место», обе видят «да», и обе продают последнее место. Триггер из лабы 3 от этого не спасает: он не видит незафиксированную вставку другой сессии.

**Способы исправления:**

- `SELECT ... FOR UPDATE` блокирует строку до конца транзакции, вторая сессия ждёт. Блокировать нужно общую строку (сеанс, счёт, склад);
- уникальное ограничение: база сама не пропустит вторую одинаковую запись;
- уровень `SERIALIZABLE`: база отменит одну из конфликтующих транзакций с ошибкой 40001.

**Уровни изоляции:**

| Уровень | Что видит транзакция |
| --- | --- |
| `READ COMMITTED` (по умолчанию) | Каждый запрос видит данные, зафиксированные к его началу. Два одинаковых запроса могут вернуть разное (неповторяющееся чтение) |
| `REPEATABLE READ` | Вся транзакция видит данные на момент первого запроса |
| `SERIALIZABLE` | Результат такой же, как при выполнении транзакций по очереди |

**Взаимоблокировка (deadlock).** Сессия A заблокировала строку 1 и ждёт строку 2, сессия B заблокировала строку 2 и ждёт строку 1. База замечает это и отменяет одну из транзакций с ошибкой 40P01. Чтобы избежать, строки блокируют в одном порядке.

**MVCC.** При изменении строки PostgreSQL создаёт её новую версию, старая остаётся видна транзакциям, которые начались раньше. Поэтому чтение не ждёт запись, а запись не ждёт чтение.

**Роли и права.** Приложение не должно подключаться к базе под суперпользователем: при взломе злоумышленник получит всё. Для приложения создаются роли с минимальными правами:

```sql
GRANT SELECT ON v_session_card TO app_reader;
REVOKE ALL ON tickets FROM app_reader;
```

`app_reader` только читает представления, `app_writer` меняет данные только через функции. Попытка сделать лишнее заканчивается ошибкой `permission denied`.

## Сценарий гонки

Формат описан в [scenarios.md](scenarios.md). Чекер открывает два подключения и выполняет шаги по порядку. Шаг `[check]` возвращает один `boolean`: `true`, если правило соблюдено.

```sql
-- [setup] Сеанс, на котором осталось одно свободное место
DELETE FROM sessions WHERE note = 'race-test';
INSERT INTO sessions (film_id, hall_id, starts_at, note) VALUES (1, 1, '2026-12-01 19:00+03', 'race-test');
-- ... занять все места, кроме одного ...

-- [A] Окно A: место свободно, продаём
BEGIN;
INSERT INTO tickets (session_id, seat_id, price) SELECT id, 100, 300 FROM sessions WHERE note = 'race-test';

-- [B] Окно B в тот же момент: триггер не видит билет окна A, тоже продаём
BEGIN;
INSERT INTO tickets (session_id, seat_id, price) SELECT id, 101, 300 FROM sessions WHERE note = 'race-test';

-- [A]
COMMIT;

-- [B]
COMMIT;

-- [check] Продано не больше, чем мест в зале?
-- expect: false
SELECT count(*) <= (SELECT seats FROM halls WHERE id = 1) FROM tickets t JOIN sessions s ON s.id = t.session_id WHERE s.note = 'race-test';

-- [cleanup]
DELETE FROM sessions WHERE note = 'race-test';
```

В `race_fixed.sql` те же шаги выполняются через исправленную операцию. У шага `[check]` ожидание `-- expect: true`, у окна, которое ждёт блокировку, `-- expect: blocked`.

## Пароли ролей

`docker-compose.yml` передаёт `APP_READER_PASSWORD` и `APP_WRITER_PASSWORD` из `.env` в контейнер. Скрипт ролей читает их командой psql `\getenv`:

```sql
\getenv reader_password APP_READER_PASSWORD
\getenv writer_password APP_WRITER_PASSWORD
CREATE ROLE app_reader LOGIN PASSWORD :'reader_password';
CREATE ROLE app_writer LOGIN PASSWORD :'writer_password' IN ROLE app_reader;
```

## ★ (2 балла): изоляция и взаимоблокировка

- `demo/isolation_rc.sql` и `demo/isolation_rr.sql`: окно A дважды читает одно значение, окно B между чтениями меняет его. На `READ COMMITTED` второе чтение возвращает новое значение, на `REPEATABLE READ` прежнее. Значения указываются в `-- expect: value ...`.
- `demo/deadlock.sql`: два окна блокируют две строки в разном порядке, база отвечает `deadlock detected` (`-- expect: error deadlock`).

## ★★ (2 балла): RLS и резервная копия

- Row Level Security: пользователь видит только свои строки. `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, `CREATE POLICY`, проверка в `demo/rls.sql` под ролью пользователя. Владелец таблицы и суперпользователь политики не замечают.
- Резервная копия: `pg_dump`, восстановление в чистую базу через `pg_restore`, данные на месте. Скрипт в `scripts/` или команды в README.

## Подсказки

- Права удобно проверять без пароля: `SET ROLE app_reader;`, затем запрос, затем `RESET ROLE;`.
- По умолчанию функции может вызывать кто угодно (`PUBLIC`). Сначала: `REVOKE EXECUTE ON ALL ROUTINES IN SCHEMA public FROM PUBLIC;`.
- Функция для `app_writer` объявляется как `SECURITY DEFINER SET search_path = public, pg_temp`: она работает с правами владельца.
- `[setup]` должен удалять остатки прошлого прогона, иначе со второго раза сработает `UNIQUE`.
