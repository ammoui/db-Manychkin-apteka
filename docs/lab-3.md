# Лаба 3. Логика в базе

**Цель:** база сама следит за правилами темы и выполняет бизнес-операции одной командой.

**Срок:** Pull Request `lab-3` в `main` до 23:59 накануне встречи 4.

## Теория

**Где хранить логику.** Правило, записанное в базе, работает для всех: для сайта, для скрипта, для человека в `psql`. Правило в коде приложения легко обойти, если писать в базу напрямую. В базу стоит выносить то, что касается целостности данных: «на сеанс нельзя продать больше мест, чем в зале». Отправку писем и работу с внешними сервисами оставляют приложению.

**Представление (VIEW)** это сохранённый запрос с именем. Данных оно не хранит: при каждом обращении запрос выполняется заново, поэтому результат всегда актуальный.

```sql
CREATE VIEW v_session_card AS
SELECT s.id, f.title, h.name AS hall, s.starts_at
FROM sessions s JOIN films f ON f.id = s.film_id JOIN halls h ON h.id = s.hall_id;
```

**Материализованное представление** хранит результат запроса как таблица. Читается быстро, но обновляется только командой `REFRESH MATERIALIZED VIEW`.

**Функция** принимает параметры и возвращает значение или таблицу. Вызывается внутри запроса: `SELECT free_seats(42);`. **Процедура** ничего не возвращает и вызывается командой `CALL`, внутри неё можно управлять транзакцией. Функции и процедуры пишутся на SQL или PL/pgSQL.

**Бизнес-операция одной командой**: функция, которая выполняет действие целиком. Например, `buy_ticket(session_id, seat_id)` проверяет место, создаёт билет и возвращает его номер.

**Триггер** это функция, которую база вызывает сама при `INSERT`, `UPDATE` или `DELETE`.

| | `BEFORE` | `AFTER` |
| --- | --- | --- |
| Когда | До записи строки | После записи строки |
| Для чего | Проверить правило, поправить значения в `NEW`, отменить операцию ошибкой | Записать историю, обновить связанные данные |

Внутри триггера `NEW` содержит новую версию строки, `OLD` старую. `RAISE EXCEPTION 'текст'` прерывает операцию с ошибкой, и изменения откатываются.

```sql
CREATE FUNCTION check_seats() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF (SELECT count(*) FROM tickets WHERE session_id = NEW.session_id)
       >= (SELECT h.seats FROM sessions s JOIN halls h ON h.id = s.hall_id WHERE s.id = NEW.session_id) THEN
        RAISE EXCEPTION 'На сеанс % больше нет мест', NEW.session_id;
    END IF;
    RETURN NEW;
END $$;

CREATE TRIGGER trg_check_seats BEFORE INSERT ON tickets
FOR EACH ROW EXECUTE FUNCTION check_seats();
```

**Аудит.** Служебный триггер может заполнять `updated_at` или записывать в таблицу истории, кто, что и когда изменил.

**Риски триггеров.** Логика скрыта: глядя на `INSERT`, не видно, что сработает ещё. Триггер выполняется для каждой строки и замедляет массовые операции. Триггер, который меняет свою же таблицу, может вызвать сам себя.

## Подсказки

- В тексте ошибки можно подставлять значения: `RAISE EXCEPTION 'Мест нет: продано % из %', sold, total;`.
- `BEFORE`-триггер срабатывает раньше проверки внешних ключей. Если родительской строки нет, лучше сделать `RETURN NEW` и дать внешнему ключу вернуть свою ошибку.
- Функцию, которая меняет данные, не стоит вызывать в `WHERE`: она выполнится для каждой строки.
- `now()` одинаков во всей транзакции, `clock_timestamp()` возвращает текущее время.
- Триггеры одного типа на одной таблице срабатывают в порядке имён.
