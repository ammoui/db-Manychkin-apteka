# Лаба 1. Модель данных и схема

**Цель:** спроектировать базу своей темы и создать её так, чтобы база сама не принимала неправильные данные.

**Срок:** Pull Request `lab-1` в `main` до 23:59 накануне встречи 2.

## Теория

**Реляционная модель.** Данные хранятся в таблицах. Строка таблицы описывает один объект (фильм, клиента, заказ), столбец описывает одно его свойство. У каждого столбца есть тип: `integer`, `text`, `numeric`, `timestamptz` и другие.

**Первичный ключ (PRIMARY KEY)** однозначно определяет строку: значение уникально и не может быть `NULL`. Обычно это искусственный номер:

```sql
id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

**Внешний ключ (FOREIGN KEY)** связывает строку с другой таблицей: `film_id integer REFERENCES films (id)`. База не даст вставить номер фильма, которого нет, и не даст удалить фильм, на который есть ссылки (если не указано иное в `ON DELETE`).

**Виды связей:**

| Связь | Пример | Как хранится |
| --- | --- | --- |
| 1:N | В зале много сеансов | Внешний ключ `hall_id` в таблице сеансов |
| 1:1 | У человека один паспорт | Внешний ключ с `UNIQUE` |
| N:M | У фильма много жанров, у жанра много фильмов | Отдельная связующая таблица `film_genres (film_id, genre_id)` с двумя внешними ключами |

**ER-диаграмма** показывает сущности (будущие таблицы), их атрибуты и связи между ними. В этом курсе диаграмма рисуется в README блоком Mermaid `erDiagram`, GitHub отображает её сам.

**Ограничения** защищают данные от ошибок:

| Ограничение | Что запрещает | Пример |
| --- | --- | --- |
| `NOT NULL` | Пустое значение | `title text NOT NULL` |
| `UNIQUE` | Повтор значения | `email text UNIQUE`, `UNIQUE (session_id, seat_id)` |
| `CHECK` | Значение, не подходящее под условие | `CHECK (price > 0)`, `CHECK (ends_at > starts_at)` |
| `FOREIGN KEY` | Ссылку на несуществующую строку | `REFERENCES films (id)` |

**Нормализация** убирает повторы данных. Если адрес клиента записан в каждом его заказе, то при переезде его придётся менять во многих строках, и где-нибудь он останется старым. Решение: вынести клиента в отдельную таблицу и ссылаться на него по ключу.

- 1НФ: в каждой ячейке одно значение, без списков через запятую.
- 2НФ: каждый неключевой столбец зависит от всего ключа, а не от его части.
- 3НФ: неключевые столбцы не зависят друг от друга (город не определяется через почтовый индекс в той же таблице).

**Типы данных.** Деньги хранятся в `numeric(10, 2)`: `float` хранит числа приближённо, и 0.1 + 0.2 в нём не равно 0.3. Моменты времени хранятся в `timestamptz`, он учитывает часовой пояс.

## Подсказки

- Связующая таблица N:M: `PRIMARY KEY (film_id, genre_id)` и два `REFERENCES`.
- Ограничение на несколько колонок: `CHECK (ends_at > starts_at)`, `UNIQUE (session_id, seat_id)`.
- Скрипты выполняются по порядку имён: `01_schema.sql` раньше `02_seed.sql`. Таблица, на которую ссылаются, создаётся раньше той, которая ссылается.
- Если база не запустилась, ошибка видна в логе: `docker compose logs db`. Там указан файл, строка и текст ошибки.
- Пример сценария есть в комментариях `demo/lab1.sql`.
