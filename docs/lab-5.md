## Теория

**Как хранится таблица.** Таблица лежит на диске страницами по 8 КБ. Без индекса база ищет строку полным перебором: читает все страницы подряд. В плане запроса это `Seq Scan`.

**Индекс** это отдельная структура, по которой база находит нужные строки, не читая всю таблицу. Основной вид индекса в PostgreSQL: B-дерево. Ключи в нём отсортированы, поиск идёт от корня к листу за несколько шагов даже на миллионах строк.

**Цена индекса.** Индекс занимает место на диске. При каждой вставке, изменении и удалении строки база обновляет и все индексы таблицы, поэтому запись становится медленнее.

**План запроса:**

- `EXPLAIN запрос` показывает план, который выбрал планировщик, и оценку стоимости (`cost`);
- `EXPLAIN ANALYZE запрос` выполняет запрос и показывает реальное время (`actual time`) и число строк.

| Узел плана | Что делает |
| --- | --- |
| `Seq Scan` | Читает всю таблицу |
| `Index Scan` | Находит строки по индексу и читает их из таблицы |
| `Index Only Scan` | Берёт все нужные данные из индекса, таблицу не читает |
| `Bitmap Heap Scan` | Собирает по индексу список страниц и читает только их |

**Виды индексов:**

| Индекс | Пример | Когда нужен |
| --- | --- | --- |
| Обычный | `CREATE INDEX ON tickets (session_id)` | Поиск по одной колонке, внешний ключ |
| Составной | `CREATE INDEX ON tickets (session_id, sold_at)` | Условие по нескольким колонкам. Сначала колонки с `=`, потом колонка диапазона или сортировки |
| Частичный | `CREATE INDEX ON orders (created_at) WHERE status = 'new'` | Запросы только по части строк |
| Функциональный | `CREATE INDEX ON users (lower(email))` | Условие с функцией над колонкой |
| Покрывающий | `CREATE INDEX ON tickets (session_id) INCLUDE (price)` | Чтобы запрос обходился без чтения таблицы |
| GIN | `CREATE INDEX ON films USING gin (to_tsvector('russian', title))` | Полнотекстовый поиск |

**Когда индекс не помогает:**

- условие с функцией над колонкой, если нет функционального индекса: `WHERE lower(email) = ...`;
- поиск по середине строки: `LIKE '%кот%'`;
- условие подходит большой доле строк: читать всю таблицу дешевле;
- таблица маленькая.

**Генерация данных** одним запросом:

```sql

SELECT 1 + (random() * 999)::int, g, 300 + (random() * 500)::int
FROM generate_series(1, 100000) AS g;
```

## Как показать «до» без пересоздания базы

```sql
-- 2. Запрос 1 до индекса
-- expect: plan seq
BEGIN;
DROP INDEX tickets_session_idx;
EXPLAIN ANALYZE SELECT * FROM tickets WHERE session_id = 42;
ROLLBACK;                                   -- индекс вернулся

-- 3. Запрос 1 после индекса
-- expect: plan index
EXPLAIN ANALYZE SELECT * FROM tickets WHERE session_id = 42;
```

Если удалить только один индекс, планировщик может выбрать другой подходящий. В таком случае в шаге «до» удаляются все индексы, которые могут помочь.

## Подсказки

- `SELECT setseed(0.5);` в начале скрипта делает случайные данные одинаковыми при каждом пересоздании.
- Триггеры из лабы 3 замедляют массовую вставку. На время загрузки их можно отключить: `SET session_replication_role = replica;`, после загрузки пересчитать то, что они заполняли.
- После загрузки выполните `VACUUM ANALYZE <таблица>;`: планировщик получит свежую статистику.
- `date_trunc` по `timestamptz` нельзя проиндексировать, условие лучше переписать в диапазон: `WHERE sold_at >= '2026-10-01' AND sold_at < '2026-11-01'`.
